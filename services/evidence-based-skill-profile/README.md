# Evidence-Based Student Skill Profile Builder (`evidence-based-skill-profile`)

**Component:** C02, AI-Driven Evidence-Based Student Skill Profile Builder
**Owner:** P.W.Y.D Pathiraja (IT23245310)

C02 builds a student's skill profile from their own documents: CV, project descriptions, academic or
syllabus documents, certificates, and portfolio or GitHub links. It finds the skills, records how
each skill is supported (for example used in a project, or only listed in the CV), gives each skill
a confidence score from the combined evidence, lets the student verify the result, and sends the
profile to C03 (Semantic Skill Gap Analysis and Career Readiness).

Skills are identified by the canonical `SK-` IDs of the Shared Skill Knowledge service (SSKS), so
C02's profiles can be compared directly with C01's industry profiles.

## What is built so far

### Service setup

A FastAPI service with the same layout as the other services: settings from environment variables,
a database session for PostgreSQL, and a health check.

### Evidence types (TAF task 1)

`app/schemas/evidence.py` defines how a skill can be supported:

| Evidence type | Example |
|---|---|
| `project_demonstrated` | "Built the backend with FastAPI" |
| `certificate_supported` | "AWS Certified Cloud Practitioner" |
| `portfolio_supported` | GitHub repository written in TypeScript |
| `academic_exposure` | Covered in a university module |
| `cv_self_reported` | Listed in the CV skills section |
| `unverified_mention` | "Interested in learning Kubernetes" |

It also defines the source types a student can submit: `cv`, `project_description`,
`academic_document`, `certificate`, `portfolio_link`.

### Reference skill dictionary (TAF task 1)

`data/dictionary/clean_skills.csv` holds **1,853 skills**, each with an ID, a standard name, aliases
and domain tags (IT, Business, HR). It is generated by `scripts/build_dictionary.py` from:

1. The SSKS seed (`services/shared-skill-knowledge/seed/import_ready/`): skills from ESCO v1.2.1 and
   O\*NET with `SK-` IDs. C02 only reads these files.
2. C02's own files in `data/dictionary/`:

| File | Purpose | Entries |
|---|---|---|
| `alias_map.csv` | Names students use, e.g. "JS" → JavaScript, "React.js" → React, "MS Excel" → Microsoft Excel | 78 |
| `custom_skills_supplement.csv` | Skills SSKS does not have yet (e.g. NLP, Deep Learning), with `C02-` IDs | 11 |
| `alias_blocklist.csv` | Aliases that point to the wrong skill (e.g. "Mocha" on JavaScript) | 4 |

Rules applied by the build:

- When a term is one skill's name and another skill's alias, the name wins. This resolves skills
  stored twice in the seed (e.g. Python as `SK-000591` and `SK-000899`).
- An alias in `alias_map.csv` is moved to the given skill and removed from all others.
- If SSKS later adds a skill from the supplement, the C02 copy is skipped and the SSKS skill is used.
- Terms still shared by several skills are listed in `alias_conflicts.csv` for review (6 left).

### Handover to SSKS

`scripts/export_for_ssks.py` compares C02's files with the SSKS seed and writes suggestions for the
SSKS owner to `data/ssks_handover/`: 11 new skills, 76 aliases to add, and 43 aliases to remove or
fix. C02 does not edit SSKS files.

### CV skill extraction (TAF tasks 3, 4 and 6)

`app/extraction/` turns a document into a list of skill mentions:

1. **Read** (`reader.py`): PDF with `pdfplumber`, DOCX with `python-docx`, TXT.
2. **Clean** (`cleaner.py`): fixes broken characters, removes bullets, empty and repeated lines,
   and joins sentences split across lines by the PDF layout.
3. **Split into sections** (`sections.py`): Summary, Skills, Experience, Projects, Education,
   Certifications, Accomplishments. Headings were collected from the Kaggle IT and HR resumes
   ("Highlights", "Work History", "Education and Training", ...).
4. **Find skills** (`matcher.py`): every name and alias in the dictionary is a spaCy
   `PhraseMatcher` pattern. Case is ignored, except for terms of 2 characters or fewer ("C", "R",
   "Go"), which must match exactly. When matches overlap, the longest wins ("Microsoft Excel" over
   "Excel"). `data/dictionary/matcher_rules.csv` adjusts terms that are also ordinary words: "Ada"
   matches only with that spelling (not "ADA", the disability act), and "Science" is skipped
   because it matches degree names.
5. **Evidence type** (`app/evidence/rules.py`, v1 rules): Skills or Summary section →
   `cv_self_reported`; Experience or Projects with an action word ("built", "configured") →
   `project_demonstrated`; Education → `academic_exposure`; Certifications →
   `certificate_supported`; "interested in", "familiar with" → `unverified_mention`.

Each mention keeps the skill ID, the text found, its position, section, sentence and method.

Results on the Kaggle Resume Dataset (230 resumes: 120 IT, 110 HR): every file read, headings found
in 229, on average 12 skills per resume (IT 14, HR 10).

### Semantic skill knowledge base (for TAF tasks 4 and 5)

`app/semantic/` matches skills by **meaning**, not only by exact words:

- Every dictionary skill now has a `description` (from ESCO/O\*NET via SSKS; the 11 C02 skills have
  hand-written ones).
- `encoder.py` turns text into a meaning vector with the pretrained sentence-transformer
  `all-MiniLM-L6-v2` (a small BERT model), running on CPU.
- `skill_index.py` stores each skill as several vectors (name, each alias, and
  "name: description") in a FAISS index and searches it by cosine similarity. A skill's score is
  its best-matching vector.
- `scripts/build_skill_index.py` builds the `ssks` index (1,853 skills, 7,096 vectors) and, with
  `--esco`, an `esco` fallback index of ESCO skills that SSKS does not have, to find new-skill
  candidates. Indexes go to `data/index/` (not committed; rebuild them).

Examples from the `ssks` index:

| Phrase | Closest skill | Score |
|---|---|---|
| "made neural networks" | Deep Learning | 0.65 |
| "handled staff hiring and onboarding" | recruit employees | 0.70 |
| "analysed sales data in spreadsheets" | carry out sales analysis | 0.72 |
| "built REST APIs" | RESTful API | 0.89 |
| "Javascrpit" (typo) | Java (wrong) | 0.66 |

Embeddings capture meaning but not spelling, so typos are handled by fuzzy matching in the
normalisation step, which comes next.

### Hybrid skill extraction: GLiNER layer (TAF task 4)

The pipeline now finds skills with two layers (`app/extraction/pipeline.py`):

1. **Dictionary** (spaCy `PhraseMatcher`): exact names and aliases. Very precise.
2. **GLiNER** (`app/extraction/neural.py`): the pretrained zero-shot NER model
   `urchade/gliner_small-v2.1` (Zaratiana et al., NAACL 2024) marks skill phrases in any wording,
   one sentence at a time. Each phrase gets a skill ID from the normalisation engine. Phrases that
   overlap a dictionary match are skipped.

Filters that keep the GLiNER layer precise (each added after reading its output on Kaggle CVs):

| Filter | Problem it fixes |
|---|---|
| Distractor labels: GLiNER is asked for `skill`, `tool`, `technology`, `job title`, `degree`, `organization`; only the first three are kept | Job titles ("Receptionist") and degrees labelled as skills |
| A meaning-only link needs cosine ≥ 0.65 (`NEURAL_SEMANTIC_MIN`); weaker ones go to `unlinked` | Loose links ("clerical" → hire human resources) |
| Very general single words are ignored ("software", "technology", "skills") | "software" → Software libraries |
| No fuzzy matching for acronyms in capitals; the first letter must match | "SPARC" → Spark, "IT systems" → "ML systems" |

Each mention records the layer (`method`: `dictionary` or `gliner`), how it was linked
(`match_method`) and `match_score` (GLiNER certainty × link score). Phrases GLiNER finds that get no
skill ID are returned in `unlinked`: new-skill candidates for SSKS.

**Dictionary vs hybrid on 40 Kaggle resumes** (`python -m scripts.compare_extraction data/cvs --sample 40`):

| | Dictionary only | Dictionary + GLiNER |
|---|---|---|
| Skills per resume | 11.2 | 23.2 (+11.9) |
| Seconds per resume (CPU) | 1.5 | 14.9 |

Reading 30 random added skills, about 23 looked correct (for example "Visio" → Microsoft Visio,
"HRIS system" → HRIS, "creative problem solver" → Complex Problem Solving) and 7 wrong ("trained
users" → Training software, "Relationship Management" → relationship marketing). This is a first
reading, not a measurement; precision and recall are measured on hand-labelled resumes in task 10.
Frequent unlinked phrases ("network", "servers", "LAN", "WAN", "ERP", "email") and missing aliases
("Visio", "Outlook") are suggestions for SSKS.

### Skill normalisation engine (TAF task 5)

`app/normalisation/normaliser.py` maps any written skill term to one standard skill ID. It tries
methods from the most to the least certain and stops at the first that works:

| Method | What it handles | Example |
|---|---|---|
| `exact` | Dictionary name or alias, any case | "PYTHON" → Python |
| `cleaned` | Versions and suffixes removed | "Python3", "ReactJS", "Node JS" |
| `fuzzy` | Spelling mistakes (Damerau-Levenshtein with `rapidfuzz`: 1 edit for 5–8 letters, 2 for longer; shorter terms and ties are never guessed) | "Javascrpit" → JavaScript |
| `semantic` | Same meaning, other words: BERT index search, accepted at cosine ≥ 0.55, top candidates re-ranked by a cross-encoder (`ms-marco-MiniLM-L6-v2`) | "made neural networks" → Deep Learning |
| `esco_candidate` | Not in the dictionary but close to an ESCO skill (when the `esco` index is built): a new-skill suggestion for SSKS | |
| `unmatched` | Nothing close enough | "references available on request" |

Each result has the skill ID, the method, a match score (0–1) and the semantic candidates
considered. `POST /api/v1/profile/normalise` exposes it.

**Ablation on the development set** (`data/evaluation/normalisation_dev.csv`, 53 hand-written terms;
`python -m scripts.evaluate_normalisation`):

| Configuration | exact | cleaned | typo | paraphrase | not a skill | overall |
|---|---|---|---|---|---|---|
| exact only | 10/10 | 5/10 | 0/10 | 0/15 | 8/8 | 43.4% |
| + cleaning | 10/10 | 10/10 | 0/10 | 0/15 | 8/8 | 52.8% |
| + fuzzy | 10/10 | 10/10 | 9/10 | 0/15 | 8/8 | 69.8% |
| + semantic (BERT) | 10/10 | 10/10 | 9/10 | 9/15 | 6/8 | 83.0% |
| + re-rank (service default) | 10/10 | 10/10 | 9/10 | 10/15 | 6/8 | 84.9% |

Each layer fixes a different kind of term. The semantic layer adds 2 false matches on non-skills
("manager" → liaise with managers), which is why extraction (task 4) should pass only skill-like
phrases to it. This is a small development set, used to build and check the engine; the final
evaluation (task 10) uses a separate, larger set labelled before it is run.

### Evidence classification v2: SetFit (TAF task 6)

`app/evidence/classifier.py` classifies the evidence type of CV sentences with **SetFit**
(Tunstall et al., 2022): a few-shot method that fine-tunes the `all-MiniLM-L6-v2` sentence-transformer
on a small set of labelled sentences. The model reads the section and the sentence together
("experience: Responsible for the Python backend"), the same information the rules use.

- **Data:** `data/evaluation/evidence_labels.csv`, 156 sentences from the Kaggle resumes (144
  sampled evenly over CV section × rule decision, 12 "knowledge of…" hard cases), 6 skipped;
  stratified split 105 train / 45 test. Labelling rules: `data/evaluation/LABELLING_GUIDE.md`.
  Personal details (a name, a phone number, a LinkedIn link) were replaced with placeholders.
- **Classes:** the model decides the evidence type of every CV sentence. It learns
  `project_demonstrated`, `cv_self_reported`, `academic_exposure`, `certificate_supported`.
  `unverified_mention` ("interested in…") did not occur in a 144-sentence sample of these
  professional resumes, so it is not learned yet; real examples from student CVs will be added.
- **Rules:** the v1 rules are no longer used for CV decisions. They are the baseline in the
  comparison below and a fallback (with a warning) when no trained model exists. Uploaded
  certificates, GitHub links, academic documents and project reports keep their document type.
- **Train and compare:** `python -m scripts.train_evidence_model` (about 14 minutes on CPU) trains on
  the train rows, compares SetFit with the rules on the test rows, and saves the model to
  `models/evidence-setfit/` (not committed; re-train from the CSV).
- **Default:** `EVIDENCE_CLASSIFIER=setfit`; set `rules` to use the v1 baseline instead.

**Provisional result** on the 45 test sentences (labels suggested by the assistant, not yet checked
by the researcher):

| Method | Accuracy | Macro F1 |
|---|---|---|
| Rules (v1) | 42.2% | 0.564 |
| SetFit (v2) | 86.7% | 0.859 |

The rules mostly fail on claims inside Experience ("Extensive working knowledge of…" is not project
work), duties without a listed action verb ("Compose service reports monthly"), adjectives read as
verbs ("Organized HR Generalist"), and certifications outside the Certifications section.

### Multi-document profile (TAF task 2)

`app/profile/builder.py` builds one profile from several documents. Each document is read with its
source type (`cv`, `project_description`, `academic_document`, `certificate`), its skills are found
as above, and then each skill's evidence from **all** documents is fused into one confidence. Proof
from independent documents adds up, and support from several kinds of document raises it further.
Repeated names get " (2)" so two files called `cv.pdf` stay separate pieces of evidence.

Demo with the made-up documents in `data/samples/` (`python -m scripts.build_profile`):

| Skill | CV only | CV + project report + certificate |
|---|---|---|
| Python | 0.25 weak | 0.92 strong |
| React | 0.25 weak | 0.59 moderate |
| FastAPI | 0.19 weak | 0.56 moderate |
| Docker | 0.08 weak (listed) | 0.51 moderate (used in the project) |
| JavaScript | 0.08 weak | 0.08 weak (no other proof) |

Known gap seen in the demo: "interested in learning Kubernetes" is classified `academic_exposure`,
because the SetFit model has no `unverified_mention` examples yet (see task 6).

### Automatic document type (TAF task 2)

The type of each uploaded file decides how strong its evidence is (a certificate file is among the
strongest kinds), so it is **never taken from the student**: a CV uploaded as "certificate" would
otherwise get the strongest weight. `app/collection/document_type.py` detects it from the content:

1. **Structure:** at least two standard CV sections (skills, experience, education, summary,
   projects, certifications) → CV.
2. **Meaning (zero-shot):** otherwise the opening of the document is embedded with the same
   sentence-transformer as the skill index and compared with short descriptions of a certificate,
   a project report and an academic document; the closest wins. A CV is recognised only by its
   structure (a short project report was otherwise judged slightly closer to "CV").

Portfolio evidence comes only from GitHub links, which can be checked; an uploaded work sample is a
project document. The API has no type field; each document in the profile shows the detected type,
how it was detected and the similarity. Check: 229 of the 230 Kaggle resumes are detected as CVs
(the other has no section headings); the 3 demo documents and 5 short hand-written examples (a
transcript, a syllabus, a Coursera certificate, an internship report, an HR policy document) are
all detected correctly. This detects the kind of document, not whether it is genuine; checking
certificates with their issuer is future work.

### GitHub portfolio links (TAF task 2)

`app/collection/github.py` reads a GitHub user or repository link through the public GitHub REST
API (`POST /api/v1/profile/build` field `portfolio_links`, or `--github` in the script). For each of
the student's own repositories (no forks, archived or empty ones; at most 8, most recently pushed
first):

| Part | What is read | Kind of evidence |
|---|---|---|
| Code | Languages with at least 5% of the code; libraries in `requirements.txt`, `pyproject.toml`, `package.json`; repository topics | Portfolio (rank 1–2): the code shows the skill |
| README | The project description, through the normal extraction pipeline | Project description (rank 3), as a separate document `<repo> (README)` |

Languages, libraries and topics are matched by exact name only (with a small package-name map,
e.g. `torch` → PyTorch, `opencv-python` → OpenCV), never by AI guessing, so packages such as
`requests` do not become skills. Each repository is a separate document, so several repositories
using a skill are independent proof. Only public data is read; without a token GitHub allows 60
API requests an hour (`GITHUB_TOKEN` raises it to 5,000); file contents come from
raw.githubusercontent.com, which does not count. Non-IT work samples (HR documents, business
plans, designs) are uploaded as files and count as project documents.

Live check on a public account (4 repositories): Python, FastAPI, Docker and Linux came from the
code and were strong (0.88–0.91); skills only named in READMEs ("Design", "Google") stayed at 0.45.

### Evidence-fusion confidence (TAF task 7)

`app/evidence/fusion.py` combines all evidence for a skill into one confidence from 0 to 1.

**1. One ranking of the kinds of evidence.** A kind is a source type + evidence type. Only the
order is decided, by one principle: the more someone else can check it, the stronger it is. A
separate document beats a line in the CV the student wrote; checkable beats claimed. Certificates
and portfolios share the top rank, because evidence on which employers value more is mixed and
depends on the field; a portfolio is any work sample (GitHub for IT, documents or designs for HR
and Business), so non-IT students are scored the same way.

| Rank | Kind of evidence | Strength |
|---|---|---|
| 1–2 | Certificate file = portfolio / work sample | 0.900 |
| 3 | Project or internship report | 0.514 |
| 4 | Academic document | 0.385 |
| 5 | CV: certificate named | 0.288 |
| 6 | CV: project or work described | 0.211 |
| 7 | CV: course or degree named | 0.146 |
| 8 | CV: skill listed | 0.091 |
| 9 | CV: interest only | 0.043 |

**2. Rank Order Centroid (ROC)** turns the order into weights, w_k = (1/n) Σ_{i=k..n} 1/i
(Barron & Barrett, 1996, *Management Science* 42(11), 1515–1523); tied kinds share the average of
their positions; weights are scaled so the top kind is 0.9 (even a certificate is not absolute
proof). The ROC values are checked against the published ones in `tests/test_fusion.py`.

**3. Noisy-OR** (Pearl, 1988) combines the evidence: s = strength × match score × 0.5^k (k-th
repeat of the same kind in the same document), E = 1 − Π(1 − s), and a small boost for support
from several source types: C = E × (0.85 + 0.15 × share of source types). Missing evidence never
lowers a score. Levels: strong ≥ 0.70, moderate ≥ 0.40, weak below.

**4. Sensitivity analysis (SMAA-style)** (Lahdelma, Hokkanen & Salminen, 1998, *European Journal of
Operational Research* 106(1), 137–143), `python -m scripts.sensitivity_analysis`: every confidence
is recomputed with 1,000 random settings that keep the evidence order (weights drawn uniformly
from all ordered weight vectors, whose centre is exactly ROC; top strength 0.80–0.95; repeat factor
0.3–0.7; diversity boost 0–0.3). Result on 42 profiles (2 demo, 40 Kaggle resumes; 489 skills):

| Test | Skills keep their level | Rank stability (Kendall's tau) | Mean change |
|---|---|---|---|
| Random weights, same order | 90.4% | 0.942 | 0.078 |
| Certificate ranked above portfolio | 96.1% | 0.992 | 0.032 |
| Portfolio ranked above certificate | 95.3% | 0.992 | 0.033 |

By default level, the share kept is weak 93.0% (451 skills), strong 88.7% (5), moderate 54.2% (33).
The **order** of a student's skills is robust to the weights; the **label** of skills near the
middle of the scale is not, so "moderate" should be read as uncertain. The Kaggle data has only
CVs, so few skills reach moderate or strong; profiles with several documents are needed for a
fuller test. Student verification (the fifth TAF factor) is added with the profile (task 8).

## Configuration

Settings come from environment variables or a local `.env` file:

| Variable | Default | Description |
|---|---|---|
| `SERVICE_NAME` | `evidence-based-skill-profile` | Service identifier |
| `DATABASE_URL` | `postgresql+asyncpg://skillbridge:skillbridge@localhost:5432/profile_db` | PostgreSQL connection URL |
| `DICTIONARY_PATH` | `data/dictionary/clean_skills.csv` | Reference skill dictionary |
| `MATCHER_RULES_PATH` | `data/dictionary/matcher_rules.csv` | Case and skip rules for ambiguous terms |
| `EMBEDDING_MODEL` | `sentence-transformers/all-MiniLM-L6-v2` | Sentence-transformer used for the semantic index |
| `INDEX_DIR` | `data/index` | Where the FAISS skill indexes are stored |
| `RERANKER_MODEL` | `cross-encoder/ms-marco-MiniLM-L6-v2` | Cross-encoder for re-ranking semantic candidates |
| `USE_RERANKER` | `true` | Turn re-ranking on or off |
| `USE_NEURAL_EXTRACTION` | `true` | Turn the GLiNER layer on or off (off: dictionary only) |
| `GLINER_MODEL` | `urchade/gliner_small-v2.1` | GLiNER model |
| `GLINER_LABELS` / `GLINER_KEEP_LABELS` | see `settings.py` | Labels asked for / labels kept |
| `GLINER_THRESHOLD` | `0.5` | Minimum GLiNER certainty for a phrase |
| `NEURAL_SEMANTIC_MIN` | `0.65` | Minimum cosine for a GLiNER phrase linked by meaning only |
| `EVIDENCE_CLASSIFIER` | `setfit` | Evidence type for CV sentences: `setfit` (v2) or `rules` (v1 baseline) |
| `EVIDENCE_MODEL_DIR` | `models/evidence-setfit` | Where the trained SetFit model is saved and loaded |
| `GITHUB_TOKEN` | empty | Optional GitHub token (raises the API limit from 60 to 5,000 requests an hour) |
| `GITHUB_MAX_REPOS` | `8` | Repositories read per GitHub user link |
| `GITHUB_MIN_LANGUAGE_SHARE` | `0.05` | Smallest share of the code for a language to count |
| `ESCO_SKILLS_PATH` | `data/esco/skills_en.csv` | Raw ESCO skills, for the ESCO fallback index |

## Local development

### 1. Set up the environment

```bash
cd services/evidence-based-skill-profile
python -m venv .venv
.venv/Scripts/activate        # macOS/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
```

### 2. Run the service

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8002 --reload
```

Documentation is at `http://localhost:8002/api/v1/profile/docs`.

### 3. Rebuild the dictionary and the SSKS handover

Run after changing a file in `data/dictionary/` or after SSKS updates its seed:

```bash
python -m scripts.build_dictionary
python -m scripts.export_for_ssks
```

### 4. Build the semantic skill index

Run after rebuilding the dictionary or changing `EMBEDDING_MODEL`. The first run downloads the model
(about 90 MB).

```bash
python -m scripts.build_skill_index           # ssks index (about 3 minutes on CPU)
python -m scripts.build_skill_index --esco    # also the ESCO fallback index (much longer)
python -m scripts.search_skills "made neural networks" "handled staff hiring"
```

### 5. Normalise skill terms and evaluate the engine

```bash
python -m scripts.normalise_terms "Javascrpit" "Python3" "made neural networks"
python -m scripts.evaluate_normalisation --errors     # ablation table + remaining mistakes
```

### 6. Extract skills from CVs

The first run downloads the GLiNER model (about 600 MB). On slow connections set
`HF_HUB_DISABLE_XET=1`; the newer Xet download stalled on ours.

```bash
python -m scripts.compare_extraction data/cvs --sample 40 --examples 20   # dictionary vs hybrid
python -m scripts.extract_cv path/to/cv.pdf              # skill table for one CV
python -m scripts.extract_cv path/to/cv.pdf --json       # every mention as JSON
python -m scripts.extract_cv data/cvs --summary          # totals over a folder
```

### 7. Train the evidence classifier

```bash
python -m scripts.train_evidence_model        # trains SetFit, prints rules vs SetFit on the test set
```

### 8. Build a profile from several documents

```bash
python -m scripts.build_profile data/samples/sample_cv.txt \
    data/samples/sample_project_report.txt data/samples/sample_python_certificate.txt
python -m scripts.build_profile cv.pdf --github https://github.com/<user>
```

### 9. Sensitivity analysis of the confidence score

```bash
python -m scripts.sensitivity_analysis --sample 40 --draws 1000
```

### 10. Run the tests

```bash
pytest
```

## Data notes

- This service uses the ESCO classification of the European Commission, and information from O\*NET
  by the U.S. Department of Labor, Employment and Training Administration (USDOL/ETA), used under the
  CC BY 4.0 licence. The dictionary is an adapted version of ESCO v1.2.1 and O\*NET, extended with
  additional skills and aliases.
- Raw ESCO files (`data/esco/`) and student documents (`data/cvs/`, `data/resumes/`) are never committed.
